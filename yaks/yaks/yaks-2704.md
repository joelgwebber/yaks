Prototype for yaks-9bcd's storage decision (Joel, 2026-11-27: "tantivy only if it solves the whole problem without an external dep; otherwise SQLite with FTS5; measure a cold-cache build").

Build two throwaway prototypes **outside the yaks repo** (a scratch cargo project), each indexing a farm's markdown files:

- **SQLite FTS5** via `rusqlite` with the `bundled` feature: an FTS5 table over (path, kind, title, tags, body) with `unicode61 remove_diacritics 2` and prefix indexes; plain tables for link edges (source path, target, anchor) and per-file modified times from one `git log --name-only` pass.
- **tantivy**: a schema with the same text fields (positions on), and whatever tantivy offers for the edges and times; record what needs a second store.

For each, on this farm (copy it: `cp -r $(yaks path) <scratch>`) and on a synthetic farm of 10k yak files (generate realistic ones: frontmatter, 1-3 KB body, a few links):

- cold-cache full build time (drop caches as far as macOS allows: `sudo purge` is not allowed; instead build on a freshly copied directory and report it as "fresh copy"), warm rebuild, incremental update of one file;
- index size on disk; release binary size added to a hello-world;
- query latency: a word, a prefix (as-you-type), a quoted phrase, a field scope (`tag:tui`), a backlink lookup;
- whether an identifier-aware pre-tokenizer (`issues/123` → `issues`, `123`, `issues/123`; `yaks-ca59` → `yaks`, `ca59`, `yaks-ca59`) is easy to plug in;
- does it build for the five release targets (`.github/workflows/release.yml`; check documentation, not by cross-compiling all five).

Deliverable: a report attached to this yak, a `Decision:`-style recommendation note (not the decision itself: the yakherd and Joel decide), and the prototype source attached as a directory.

#### 2026-11-27T13:01:06Z

*idxproto-1*

Decision: recommendation (not the decision; for the yakherd and Joel): **SQLite FTS5 via `rusqlite` + `bundled`**, with a tantivy fallback if the numbers below change.

Reasoning:

- Joel's rule was "tantivy only if it solves the whole problem without a second store". It does (edges as a raw multi-valued field, mtimes as a fast field), so it passes, but it passes by contortion: outgoing-link lists and all-rows scans are walks, metadata changes re-index the document, and there are no joins ("matches `tui` and links to X" is two queries).
- SQLite makes edges, mtimes and field values ordinary indexed tables beside the FTS table, one file with a busy timeout, one transaction for an incremental refresh, and a `UPDATE docs SET mtime` for the staleness pass. It adds 7 crates and +1.8 MB against 49-54 crates and +4.4-5.3 MB for tantivy, which matters for a binary that is 14.7 MB today and ships on five targets.
- At this farm's scale (a few thousand files, a few MB of text) both are far under any latency a person can feel, and the build is dominated by `git log`, so tantivy's speed and size advantages (2-6x faster update batches, 5x smaller index) buy nothing the user can see.

Costs to accept:

- A C compiler becomes a build requirement on all five release targets (no workflow change needed; fix the `release.yml` comment).
- The identifier tokenizer is `unsafe` FFI over `libsqlite3-sys`; confine it to one small module with its own test. If that is unacceptable, tantivy's tokenizer is the safer one.
- Index is 5x larger (62 MB at 10k files; 28 MB without the `prefix=` indexes, which bought little: 2-char prefix 3.0 vs 5.4 ms). Pick prefix indexes by measuring on the real farm, not by default.
- Bulk updates are slower and noisy; refresh incrementally from `git log <last-indexed>..HEAD --name-only`, not per-file `git log`.

Would flip to tantivy if: the farm is expected past roughly 100k documents, if relevance ranking beyond BM25 or fuzzy matching is wanted, or if a C toolchain on the release targets is ruled out. In that case use `default-features = false, features = ["mmap","lz4-compression"]` and a single writer thread for small corpora.
