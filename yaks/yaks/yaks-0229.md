Part of yaks-4cfe. Some things in a farm are a *set* of files: a directory source's `files/` tree (YASS: 170 files), a yak's attachment directory `<herd>/yaks/<id>/`, and a dok's sibling directory (yaks-db66). The TUI has no way to look through one. You see only whatever is linked from a body, or `source.md`'s `files:` list as raw YAML.

A yak in another farm wanted to attach experimental code. `yaks attach` refuses a directory (`error reading d: Is a directory`), so the agent attached a `.tgz`. System-open (`O`) on it ran the OS's archive utility, which unpacked it into the farm.

## Proposal

1. **A file browser in the right pane.** On any directory in the farm (a source's `files/`, a yak's or dok's attachment directory), it lists entries as a tree. `Enter` opens a file in the existing text or image viewer, or descends into a directory. `O` takes the file out, like everywhere else. It is reached from a source's view, from a yak's detail (a row like "attachments (n)" when the directory has files), and by following a link to a directory.
2. **`yaks attach <dir>`** keeps the directory's layout under the attachment directory, with the limits and skip rules of directory sources (yaks-3da7). The `yaks` skill says to attach a directory, not an archive.
3. **Archives are never system-opened from the TUI.** `.tgz`, `.zip`, `.tar` and the like say "an archive: `O` → `p` copies its path". Optionally, the browser lists an archive's contents read-only (both `tar` and `zip` have Rust crates).

Once 1 exists, `source.md`'s `files:` list has no reader left. yaks-535c drops it.
