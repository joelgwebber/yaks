YASS! Yet Another Spec System.

YASS keeps the plan, progress and decisions for every change in plain files next to your code, so people and agents can plan and build together.

Install GitHub

Describe the change, not the whole system.

Your code, docs and READMEs are the source of truth for what exists. YASS doesn't write it down a second time. It specs only what needs to change, tracks progress as it's built, and keeps it all next to the code, in plain markdown that agents and humans both read. It's lightweight project management for people and coding agents.

Nothing to keep in sync

There's no second description of your system to drift out of date. When a change is done, it moves to the archive, and the archive tells the story of how the product got here.

Ceremony scales with scope

A bug fix is one file. A new system gets a PRD, a plan, the hard-to-undo calls, and PR-sized pieces, all in the same folder.

Decisions you can find

Who decided what, and why, is written down as the work happens. Plan changes get their own commits, so they can be reviewed apart from the code.

A change is a folder.

Each piece of work gets a dated folder. Progress, decisions and a log travel in it, in the same commits as the code they describe.

yass/
├── changes/                       active work
│   ├── 2026-10-02-fix-double-tap-save/
│   │   └── change.md              small: goal, acceptance, steps, decisions, log
│   └── 2026-09-14-offline-sync/
│       ├── change.md              large: goal, decisions, log…
│       ├── prd.md                 …why and what
│       ├── plan.md                …how, and acceptance criteria
│       ├── design.md              …the hard-to-undo calls (optional)
│       └── 2026-09-16-offline-queue/  …and PR-sized pieces
└── archive/                       finished changes, as they were

That's the whole system: no database, no server, no integrations to set up. One small CLI, six playbooks your agent follows, and an optional git hook. It fits the workflow you already have: plans and progress travel in the same commits and pull requests as the code, and YASS never commits for you.

You talk to your agent.

The playbooks are skills your agent already knows how to follow. You don't learn a process; you ask.

You sayPlaybookWhat happens
“Let's build offline sync”yass-shapea conversation that ends in a PRD you approve
“Plan it”yass-planapproach, acceptance criteria and PR-sized pieces; nothing gets built yet
“Fix the double-tap crash” or “Keep going”yass-workbuilds against the acceptance criteria, ticking boxes and logging as it goes, resuming from the last Next:
“Where are we?”yass-statusprogress, blockers, recent decisions, what's ready to archive
“Why did we pick SQLite?”yass-logthe decision, who made it and when, with the code that carried it out
“Update YASS”yass-updatea verified newer binary, then the repo upgraded, asking before it downloads

The playbooks are Agent Skills, read natively by Codex, OpenCode and pi, and by Claude Code with --claude. Any agent that can read files and run a shell command can follow the rules. A plan from your harness’s plan mode becomes a change.

Install

Two steps, like most tools: install the yass binary, once per machine, then set up each repo you use it in.

1. Install the binary

Terminal

Downloads the latest release for your machine, checks its checksum, and puts yass in ~/.local/bin. It does nothing else (read the script first).

curl -fsSL https://raw.githubusercontent.com/donjaime/yass/main/install.sh | bash

Rather check each step? Install from a release, with checksums and signed build provenance.

From Source

With Go 1.24 or later. This puts yass in $(go env GOPATH)/bin; or build a clone.

go install github.com/donjaime/yass/cmd/yass@latest

Agent Prompt

Paste this into your coding agent, from inside the repo you want to set up. It does both steps: it verifies the download, reads the install script, and asks before changing anything.

Install YASS (https://github.com/donjaime/yass) and set it up in this repository. Go step by step,
show me what you find, and don't run anything that changes files until I say so.

Part 1, the binary:
1. Work out this machine's OS (darwin, linux or windows) and CPU (amd64 or arm64).
2. In a temporary folder, download yass_<os>_<arch>.tar.gz (.zip on Windows) and checksums.txt
   from https://github.com/donjaime/yass/releases/latest/download/.
   If I've said "from source" instead: clone https://github.com/donjaime/yass, check out the
   latest release tag, and build it with `go build -o bin/yass ./cmd/yass` (Go 1.24 or later);
   skip step 3.
3. Check the archive's SHA-256 against its line in checksums.txt. If the GitHub CLI is installed,
   also run `gh attestation verify <archive> --repo donjaime/yass`. Stop if either check fails.
4. Unpack it and read install.sh in full. Tell me what it will do: it should only copy the yass
   binary into a folder (~/.local/bin, or the one passed to --bin-dir) and say whether that folder
   is on my PATH. Point out anything that looks unexpected.
5. Ask me where to put the binary, then once I say go, run install.sh (with --bin-dir <folder>
   if I picked another). If the folder isn't on my PATH, show me the line that adds it
   (install.sh prints one); don't edit my shell files.

Part 2, this repo:
6. Ask me which options I want: Claude Code files (--claude), playbooks in my user folder rather
   than this repo (--global), the optional pre-commit hook (--hooks), or keeping the yass folder
   outside this repo (--path <folder>).
7. Run <folder>/yass init with my options, then yass status to check it works, and show me
   git status. Don't commit; I'll review it and commit it myself.

Then put it on your PATH, so you, your agents and the git hook can run yass. The script says whether it is, and if not, prints the line for your shell. For zsh:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshenv

2. Set up a repo

From inside the repo. yass init adds the playbooks, a short section in AGENTS.md, an empty yass/ folder and the optional hook; committing them means your teammates get them, and need only the binary.

yass init
git add -A && git commit -m "chore: adopt YASS"

Then talk to your agent. The options cover Claude Code, the git hook, monorepo folders and keeping plans outside the repo.

Upgrading is the same two steps: yass update for a newer binary, verified, then yass upgrade in each repo, and commit (how it works). Trying it out? yass deinit takes YASS back out of a repo, keeping your plans unless you delete them (removing YASS).

Built for teams too.

Plain files in the repo mean nothing new to host, and they fit the process you already have, from a solo developer to teams inside larger organizations with mature processes.

Monorepos large and small

YASS can be set up once for the whole repo, or for individual teams inside the repo. Each team can get their own planning folder and separate agent configuration. It's up to you! Monorepos

Plan outside the repo (if you want)

Planning in private? YASS can do that too. Point a yass.yaml at a plans folder elsewhere: a plans repo of its own, or a private folder only your team sees, found from every worktree your agents run in. Keeping plans out of the repo

Keep CI simple

Commits that only touch plans can skip builds and tests (yass paths --only), with recipes for required checks, merge queues and Bazel. The optional hook keeps intent and code in separate commits. CI recipes · The hook
