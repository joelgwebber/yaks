purely ephemeral (as soon as you esc or navigate, it's lost). We might consider having a
persistent filtered list view that handles all filtered states, and is automatically selected when
searching a list.

One approach: Just put it to the left of "Hairy" so that you can always get back to it easily.

If we take this approach, we'll need to think carefully through the capabilities (e.g., mixed
filters) and interaction modes (how does one manage multiple filters flexibly, without creating
confusion).

  Proposal: one FilterSpec, edited in a modal overlay.

  f opens an overlay listing every filter dimension at once:

  Filter
    status     [x] hairy  [x] shaving  [ ] shorn  [ ] dead
    type       [x] task   [x] bug      [x] feature  [ ] idea
    priority   [x] p1     [x] p2       [ ] p3
    labels     urgent, core              (any-of, blank = any)
    search     retry                     (substring, title + description)
    deps       [ ] ready only   [ ] tangled only
    parent     yak-7cd3                  (blank = any)

    [Apply]  [Clear all]  [Cancel]

  Navigate rows with ↑/↓, toggle a checkbox/chip with Space, type into text fields directly. Enter applies, Esc cancels. Within-row choices OR; across rows AND. Standard.

  Tabs stay; status filter defaults to "current tab" but can be overridden in the overlay (overrides the tab). Tab counts show the filtered total, so the filter is visible everywhere.

  Status bar gets a one-line chip summary so the user always knows what's active without reopening the editor: filter: type:bug,feature p≤2 "retry"  (8). Clear via the overlay or a dedicated key like \ or Esc-Esc.

  What this replaces:
  - / → opens overlay focused on the search field. Persists.
  - n/t/a → "deps: ready only / tangled only" checkboxes. The toggles disappear.
  - The implicit "back to all" magic of Esc → explicit "Clear all" in the overlay.

  What we explicitly don't build (for simplicity):
  - Saved/named filters
  - Boolean expressions beyond AND/OR (no NOT, no parentheses)
  - Sort customization
  - Filter as a sibling tab
  - Per-tab filters (one global filter applied across the whole UI)

  Implementation shape: FilterSpec dataclass (one field per dimension) lives on App. tree.build_tree takes it as input and applies the predicate. dialogs.filter_editor(stdscr, current_spec) -> new_spec runs the modal. That's it — no new modules, just a dataclass + a dialog threading the spec through build_tree.
