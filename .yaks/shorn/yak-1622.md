▸ 2026-08-16T23:24:33Z
FINDINGS + reconciliation with yak-3fd4 (versions verified 2026-08).

HARD CONSTRAINT inherited from yak-3fd4: files are AUTHORITATIVE (status=dir, id/parent in filename+frontmatter, grep-able/editable). The index is a DERIVED, per-user, rebuildable cache under ~/.cache, never committed, and is NOT a second source of truth. yak-3fd4 explicitly REJECTED a committed symlink index and concluded the in-memory records ARE the query engine, with a single stat-validated JSON file (atomic temp+rename) as the fast-load serialization. Any embedded DB is therefore admissible ONLY as backing for that derived cache, NEVER as task state.

CANDIDATES: redb 4.1.0 (pure-Rust, ACID, MVCC concurrent readers + one writer, crash-safe, STABLE on-disk format, 1.6M/mo); fjall 3.1.9 (LSM, RocksDB-like); heed (LMDB bindings); rusqlite (SQLite); sled (largely dormant — avoid).

DECIDING AXIS = CROSS-PROCESS concurrency (our CLI and TUI run at the same time against one herd):
- fjall EXPLICITLY forbids it: "A single database may not be loaded in parallel from separate processes." => DISQUALIFIED for our model.
- redb: single-process (advisory file lock guards the file); great for one long-lived process, not for many short CLI invocations racing a TUI.
- LMDB (heed): the genuine multi-process, multi-reader/single-writer store (mmap + robust locks) — the gold standard IF we ever truly need a shared embedded DB across processes.
- SQLite (rusqlite): also real multi-process via its own locking/WAL; battle-tested; but it is a relational engine for a job that is a keyed in-memory cache.

WHY NO DB NOW: yak-3fd4 benchmarks show the current design already loads a 50k-file herd in ~30ms from one stat-validated JSON file and self-heals on corruption; filter/sort/count run in memory in <10ms. An embedded KV adds a dependency, an opaque binary file, and its own versioning/migration story for MARGINAL gain at our scale, and (redb/fjall) actively fights our multi-process pattern. The atomic temp+rename single-file pattern is inherently safe for concurrent readers (last-writer-wins; readers re-validate against fs stat regardless).

RUST MAKES THE FS-NATIVE INDEX EVEN BETTER: native (de)serialization via bincode/postcard/rkyv (or a memory-mappable layout) drops index load to sub-ms; the ~1.3s "touch 50k files" rebuild floor from yak-3fd4 parallelizes with rayon. Keep the index behind a small trait so a heed/redb backend can be swapped in IF a measured need appears well past 100k files — but do not adopt one preemptively (that would reintroduce exactly the opaque-second-store tradeoff 3fd4 rejected).

APPEND-ONLY LOG: not required by the model (status change = atomic rename; the derived index is rebuildable). If we later want undo/audit/event history, that is a plain append-only file we own, still not a DB.

CROSS-PROCESS INVALIDATION: the notify crate (FSEvents/inotify/kqueue) can replace the TUI stat-scan poll (also a yak-3fd4 follow-up); tracked under yak-90b8.

RECOMMENDATION: Port the fs-native, stat-validated, atomically-written derived index as-is; use native serialization + rayon rebuild; hide it behind a trait. No embedded DB now. If one is ever needed, it is LMDB (heed) or SQLite, never fjall/redb, because of our multi-process requirement — and even then only for the DERIVED cache.

REFINEMENT (per owner): the ask is not a real DB but COMPONENT libs for a git-like, cross-process-safe DERIVED layer. Survey (versions verified 2026-08):

- Binary serialization via serde: postcard (compact, no_std), bincode 2.x (simple/fast), rmp-serde (MessagePack). For a memory-MAPPABLE, zero-parse index: rkyv 0.8 (11.8M/mo, very mature) lets you access the archived struct directly from an mmap with NO deserialization pass. That turns index load into mmap + validate (sub-microsecond) beating even the ~30ms JSON load measured in yak-3fd4. Strongest fit for the derived index: write an rkyv archive atomically (temp+rename), readers mmap it, stat-validate against the fs, rebuild on mismatch = the git-index shape, now zero-copy.

- Append-only log + tombstones: this is the Bitcask/LSM primitive. A dedicated crate exists (okaywal 0.3, Khonsu/Nebari WAL) BUT it is early, file-format-UNSTABLE, ~300 downloads/mo, self-labeled not-for-production => do NOT depend on it. The model we need is trivial and better owned: append records to a segment file opened O_APPEND (POSIX guarantees atomic writes under PIPE_BUF ~4KB, which covers a task-event record), mark deletions with tombstone records, compact by rewriting live records to a new segment + atomic rename. Same own-the-format approach as the index; cross-process-safe with O_APPEND plus an advisory lock (fs4/fd-lock) only around compaction.

- Indexing structure: at our scale the in-memory records ARE the index (yak-3fd4); no b-tree lib needed. On-disk ordered lookup (redb/LMDB) only if measured need appears well past 100k, subject to the multi-process caveats in the prior note.

REVISED RECOMMENDATION: keep files authoritative; make the DERIVED index an rkyv zero-copy archive (mmap + stat-validate + atomic rewrite + rayon rebuild) instead of JSON — same architecture, near-instant load. Add a hand-rolled O_APPEND + tombstone + compaction segment log ONLY if we later want history/undo/audit (not okaywal). No embedded DB, no format we do not own. This is exactly the git-like, cross-process-safe sketch.
