▸ 2026-08-16T23:25:39Z
SYNTHESIS + go/no-go (rolls up yak-ef0f/6819/1622/199b/90b8).

BENEFITS — validated:
1. Single static binary, zero runtime deps. Kills Python version/venv/uv-resolution friction; crossterm also removes the ncurses C dep. True copy-one-file distribution (the old static-C-binary feel you want).
2. Startup — MEASURED on this machine, this herd (224 files, warm index): every yak.py CLI call is ~42-48ms median. Breakdown: ~16ms bare interpreter + ~25-30ms importing yaklib/argparse/yaml; the ACTUAL work (full list scan with warm index) adds only ~2-5ms over --help. So per-invocation latency is ~90% Python startup tax, ~10% real work. A Rust binary starts in ~1-5ms => roughly 10-20x lower per-call latency. This is the strongest concrete win and it compounds in the agent/CLI loop that shells out constantly. (Note: prompt_toolkit ~70ms import is already lazy, so only the TUI/editor path pays it today — but the port deletes that dep regardless.)
3. Better libraries, not just a translation: edtui (embedded modal editor, kills the terminal-takeover + prompt_toolkit), ratatui immediate-mode (kills stale-cell/force-repaint yak-be65), avt + ratatui TestBackend (kills castkit hand-rolled screen). The rewrite improves UX, it is not lateral.

SCOPE: ~7.2k LOC Python. Split: CLI/core half (model 652 + commands 846 + deps/filter/rollup/index/parser/etc.) ~2.4k, well-tested, high-value, low-risk to port; TUI half (tui.py 1183 + yaktui ~2.4k) ~3.6k, the larger and riskier chunk, but also where the real wins are.

MIGRATION PATH — incremental, reversible, no big-bang (enabled by fs-native state + per-user derived index from yak-3fd4, which lets Rust and Python operate the SAME herd side by side):
- Phase 0 SPIKE (small, do first): yak show/list/next in Rust reading the SAME .yaks/ files and the existing on-disk index. Proves parse + fs model + interop and produces the real startup delta end-to-end. High signal, low cost, reversible.
- Phase 1 CLI PARITY: port model/commands/deps/filter/rollup/index behind clap; assert byte-parity on --json against the current pytest subprocess suite. Ship the Rust binary ALONGSIDE Python; both drive the same directory (no format change => they interoperate).
- Phase 2 TUI: rebuild in ratatui + edtui + crossterm. This is the bulk of the effort and where editor/repaint/terminal-takeover pains actually get fixed. Keep the Python TUI until parity.
- Phase 3 DEMO/RECORDING: castkit -> ratatui TestBackend Buffer + tiny asciicast writer + avt (folds in yak-3291, yak-fa3b).
- Phase 4 CUTOVER: flip distribution (skill Running-yaks stanza + Claude/Codex marketplace manifests) from uvx/PyPI to a binary installer; retire Python.

COSTS / RISKS: TUI rewrite (~3.6k loc) is the real work; two impls coexist during transition; CI/distribution rework (cargo-dist, brew, binstall) + editing the skill/plugin install stanzas; contributors need Rust; YAML edge-cases vs pyyaml (mitigated — frontmatter is trivial + golden tests). None are blockers.

RECOMMENDATION: GO to Phase 0 spike, gate the full go/no-go on it. The spike converts the nebulous benefits into a measured startup number and a proven parse/interop path before we commit to the large TUI rewrite. Do NOT block the current UI arc (yak-4473 et al.) on this — the flat-id + derived-index foundation from yak-3fd4 is exactly what makes a clean, incremental port possible whenever we choose to start. Follow-up conversion yaks (Phase 0 spike, then per-phase) to be spawned on your go-ahead, not created preemptively.

REFINEMENT (per owner) + updated plan.

NEW-REPO BOOTSTRAP (adopt): start a fresh repo (e.g. yaks-rs) and PORT the design/implementation rather than converting in-place. Rationale: avoids massive mixed-language diffs and keeps the Python tree stable and shippable during the port; the two implementations interoperate at the DATA layer anyway (same .yaks/ files + derived index), so they need not share a repo. Skills/plugins can point at whichever binary is ready. Makes Phase 0/1 cleaner and lower-risk than an in-tree rewrite. Cost: history/issues split across repos and a later flip-the-canonical-repo step — both minor.

ROLL-UP of round-2 refinements:
- Storage (yak-1622): not a DB but components — derived index becomes an rkyv zero-copy archive (mmap + stat-validate + atomic rewrite + rayon rebuild); optional hand-rolled O_APPEND + tombstone log for future history. Git-like, cross-process-safe, own-the-format.
- Editor (yak-6819): edtui with user-selectable keymap profiles (vim/emacs/nano/helix) via config.
- Virtual term (yak-199b): one painter -> ratatui Buffer doubles as snapshot-test + agent-introspection surface, not just demo.
- Distribution (yak-90b8): cargo-dist driving a Biome-style npm installer (platform packages as optionalDependencies) to mirror the proven Go + goreleaser + npm flow, plus brew/shell/binstall.

REVISED NEXT STEP: Phase 0 spike in a NEW repo — implement yak show/list/next in Rust reading the existing .yaks/ + index, wire cargo-dist + an npm installer skeleton EARLY so distribution is proven from day one, and produce the measured cold-start delta vs the ~42-48ms Python baseline. Gate full go/no-go on that spike. Reversible and non-blocking to the yak-4473 UI arc. Tracked as a new top-level spike yak.
