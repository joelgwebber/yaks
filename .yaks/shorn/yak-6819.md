Find a good embeddable multi-line + single-line editor with vim (and ideally helix/generic) bindings to replace the prompt_toolkit shell-out (editor.py, the one that hijacks the terminal) and the hand-rolled vim_edit.py.

---
▸ 2026-08-16T23:24:08Z
FINDINGS (versions verified 2026-08 via lib.rs).

ROOT PROBLEM today: yaktui/editor.py suspends curses (def_prog_mode + endwin), clears the screen, hacks tty flags (disables IXON so Ctrl-S reaches the app), shells out to a prompt_toolkit inline prompt, then resumes curses. That is exactly the "takes over the whole terminal" behavior you dislike, plus the prompt_toolkit runtime dependency. yaktui/vim_edit.py is a separate hand-rolled single-line vim subset (insert/normal, dd, cw, x, D, motions) — muscle-memory only, not real vim.

PRIMARY CANDIDATE: edtui 0.11.6 (Jul 2026, actively maintained, ratatui-native). It is a text-editor WIDGET that renders INSIDE your ratatui frame — no suspend, no screen takeover, no tty hacks. Vim bindings by default with real coverage: motions (h/j/k/l/w/e/b/f/t/0/_/$/gg/G/%/{}), operators + text objects (dw/diw/diW/ciw/ci"/ci(/df/dt/cw/D), visual mode, yy/p/P, u + ctrl-r undo/redo, and dot-repeat. Also: single_line(true) mode (blocks newlines — perfect for title/search inputs, replacing vim_edit.py), text selection, system-clipboard copy/paste, absolute/relative line numbers, optional syntax highlighting, and an optional system-editor feature (Ctrl-e opens $VISUAL/$EDITOR) as a power-user escape hatch. It also offers an Emacs/modeless mode and fully customizable keybindings. ONE widget replaces BOTH editor.py and vim_edit.py and deletes the prompt_toolkit dep + the curses-suspend dance.

FALLBACK: tui-textarea 0.7.0 (Oct 2024; very widely used — 225k/mo, 269 dependents; backend-agnostic across crossterm/termion/termwiz). Multi-line, undo/redo, search (regex), selection, single-line usage documented. BUT vim is DIY: its "vim" example is a modal state machine you copy and own. More control and more battle-tested, but more code to carry, and last release is ~2y old. Good safety net if edtui modal fidelity or maintenance disappoints.

HELIX / generic embedding: impractical. helix-core / helix-view are not published as stable reusable library crates; embedding means git-pinning and tracking heavy internal churn for what is, for us, line/paragraph editing. Not worth it. edtui already gives modal (vim) + modeless (emacs) in one widget, which covers the "vim and/or helix and/or generic" ask.

RECOMMENDATION: edtui as the single embedded editor for both multi-line (description/comments) and single-line (title/search) fields, with the system-editor feature available for anyone who wants their real $EDITOR. tui-textarea as documented fallback. This is the change that most directly fixes the stated pain.

▸ 2026-08-20T02:17:59Z
REFINEMENT (per owner): lean into edtui pluggable keymaps to offer the USER a choice of editing model. edtui ships vim (modal) and emacs (modeless) handlers and exposes fully-customizable KeyEventHandler/registers, so:
- add an editor mode config key (vim | emacs | basic) to .yaks/config.yaml alongside the existing vim_mode flag, selecting the handler at construction;
- a basic/nano-like profile (arrows, Ctrl-K/U/W, Home/End, Ctrl-S save) is a small custom register for users who want no modal behavior — replaces the non-vim branch of vim_edit.py;
- helix-style (selection-first) bindings can be another custom register later.
edtui registers are DATA, not forks, so vim/emacs/nano/helix become user-selectable profiles under one configurable widget covering both single-line and multi-line editing.
