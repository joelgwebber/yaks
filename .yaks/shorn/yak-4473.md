Shared TUI refactor that both yak-a373 (saved views) and yak-597c (Recent + Working-set) build on. Generalize the fixed status tabs into an ordered, extensible View list. A View is a named (FilterSpec + sort_by + sort_dir + limit + tree|flat) that yields a task list. The three status tabs (Hairy/Shaving/Shorn) become built-in, un-deletable, always-first Views.

Decisions (locked):
- self.tab:int becomes self.view:int indexing an ordered self.views list; tab_counts becomes view_counts.
- ONE filter, not a stack. Activating a view loads its spec into the single live filter (the thing f and / already edit). Editing forks an ephemeral 'modified' view (shown with a * on the chip); you may loosen OR tighten any criterion, including removing base criteria. Save persists (update the view or fork a new one). Reuses the whole existing filter path; no base+overlay layering.
- Esc reverts the live filter to the active view's saved spec (change from today, where Esc clears outright). 'Empty' is just the spec of an All view.
- Status is uniform and removable: part of the editable filter like any other axis. Widening a status view forks an ephemeral cross-status view, clearly marked (the * indicator + Esc-revert are the guardrail). Status stays special only in STORAGE: it is the filesystem partition (see the fs/perf yak).
- Pinned views = the tab bar. Pin order = tab order, so reorder-tabs and manage-pins are one operation. Non-pinned views live in the picker.
- View picker (key v, always available; also the strip overflow affordance) lists all views; pin/unpin, reorder, rename, delete happen there where space is unlimited.
- Discoverability: ship one non-status view (Recent) pinned by default so a new user sees the affordance on day one.
- Sorting is a general View capability: sort_by in {updated, created, priority, title, id} + sort_dir. A view that sorts is FLAT (depth 0, no collapse tree) because sort ordering cannot coexist with the parent/child tree; status views stay tree views.
- Absolute timestamp-range filtering is out of scope (painful in curses); a relative 'updated within Nd' chip is a possible later add.
- View definitions are USER-SPECIFIC for now (personal storage, not committed); team/shared views are a deliberate later addition, not urgent.
- Personal/derived state (view defs, pins, collapse, sort) never lives in task files; files stay the authoritative grep-able truth, mirroring how collapsed_ids already live in the per-user cache.
