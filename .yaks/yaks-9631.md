Goal (Joel's answers on yaks-7204, 2026-10-13):
1. Shed-only rows. A yak that exists ONLY in another shed (its `YakChange.added` and not landed, in a shed that is not the current one) appears on the yak views as a dim row with a `🛖` badge naming the shed, placed by the SHED copy's status and parent: under its parent when that parent exists here, else at the root of its status view. Call them "shed-only" rows in code: `tree::Row.ghost` already means something else (the dimmed ancestor context rows), do not reuse or rename it.
2. Data: the snapshot carries each shed-only yak's full `Task` from the shed's farm (title, status, parent, labels, body, needs), read once per scan in `Snapshot::scan` (read-only: `store::discover_with(&shed.path, None)` + `store::load`, as `sheds.rs` reads shed farms). Expose ONE query beside `copies`/`open_asks`: e.g. `Snapshot::shed_only() -> Vec<(&Shed, &Task)>`, the shed this TUI runs in left out. The same yak added in two sheds: one row, the first shed in attention order, and the conflict marker (4).
3. Read-only. A shed-only row's detail is the shed copy rendered with `detail::build`, under a banner line `only in shed <name>`; every yak-mutating key (S, E, P, T, L, D, R, H, M, A, X, c/C as child, m, *) refuses with the notification `<id> is only in shed <name>: read-only here` and changes nothing; `a` on it answers its ask in that shed when it is `needs: human` (reuse `open_answer_in_shed_prompt`), else refuses like the others. `y` copies the id.
4. Conflict marker. When two or more other sheds changed the same yak (outstanding in each: `copies(id).len() >= 2`, or a shed-only yak added in 2+ sheds), the row badge shows `⚠` (e.g. `🛖2⚠`) and the detail's `Sheds:` section opens with a line saying the yak was changed in N sheds.
5. The drawer chip `copies: any | home` (default `any`). `home` hides shed-only rows AND every badge and the detail Sheds section, for a plain view of this farm. Put it where the drawer's other chips live; if it needs a `FilterSpec` field (src/filter.rs) so saved views can hold it, add it with the default omitted when views are saved (old saved views load unchanged), and say how in a Decision note.

Scope: src/tui/sheds_tab.rs (scan + the new query + fixture variants), src/tui/viewmodel.rs (`rows`, `view_count`, `flat_rows`: the tasks the views build from), src/tui/tree.rs if placement needs it, src/tui/render.rs (`list_item` badge text), src/tui/detail.rs + detail_nav.rs (banner, conflict line), src/tui/handlers.rs (the read-only guard, `a`), src/tui/drawer.rs + src/filter.rs (the chip), tests anywhere under src/tui/ (central whole-frame ones at the end of src/tui/tests.rs). Docs: docs/tui.md (Signals, Layout, the drawer, Keys), `help_content` if a key's meaning changes, README's TUI paragraph, the yaks skill's TUI sentence (.agents/skills/yaks/SKILL.md, line starting "In `yaks tui`").
Out of scope: src/sheds.rs (fix-1), the CLI, regenerating docs/assets (do NOT run the docshots generator; the coordinator does it at landing; you may ADD a scene to src/tui/docshots.rs).

Evidence (fail first): tests that a shed-only yak (i) is a row under its home parent and (ii) at the root when its parent is not here, in the view of its shed status; (iii) every mutating key refuses on it and leaves the farm untouched (use a temp farm); (iv) `a` on a shed-only ask opens the in-shed prompt; (v) `copies: home` removes shed-only rows, badges and the Sheds section; (vi) the `⚠` marker for a yak changed in two sheds; insta snapshots of a tree with a shed-only row and of its detail. Real machine: a scratch `git worktree` shed made from your own checkout, `yaks create` a child of an existing yak there, and `yaks tui --headless` from your checkout shows it under its parent with the badge (paste the frame); remove the worktree after.
