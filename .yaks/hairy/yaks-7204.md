Joel (2026-10-04, on the first shed results): most sheds differ from the main checkout by a small delta, so the concept may layer into the UI more usefully than a top-level shed picker; ill-formed so far. This is the TUI design conversation to have with Joel before any TUI code (the CLI half is built and released in v0.0.14).

Sketches to react to (the coordinator's, not decisions), with where each stands. "CLI done" means the data and a command exist and the TUI only has to call them.
- (a) A yak-centric view: for each yak, which sheds have changed it, as a badge in list/tree rows. TUI open; the per-yak CLI form is `yaks show <id> --sheds`, there is no list-wide column.
- (b) A sheds section in `yaks show` and in the TUI detail pane. CLI done (`show --sheds`, yaks-e7ed); TUI open.
- (c) A conflict warning when two sheds have changed the same yak (the same-file conflicts of yaks-df61 O52). Open, in the TUI and the CLI; `yaks sheds` / `changes` hold the data, nothing compares sheds with each other yet.
- (d) Sheds' open asks (`needs:`) flowing into the inbox. CLI done (`inbox --sheds`, yaks-2917; answering in place is `answer <id>@<shed>`, yaks-f347); TUI Inbox view open.
- (e) "What would land" per shed: its delta against its base. CLI done (`yaks changes <shed>`, yaks-e39c); marking a shed or yak `landed` is yaks-ed5e and the shed state vocabulary (see the notes of yaks-ee0a).
- Dirty yaks (changes git does not have yet): CLI done (`yaks status`, `yaks commit`); marks in the TUI open.

▸ 2026-10-05T21:14:40Z [delta-lead]
Case from Joel (2026-10-05, yaks-36b6): an ask raised in a lane (here the coordinator's thread checkout) is invisible in the human's primary checkout: 'yaks inbox' there reads only that farm, so Joel could not see yaks-36b6 without digging into the worktree. 'yaks lanes' already shows '<id> needs: human' per lane but not the question text, and nothing writes an answer back. Two separate needs, to settle in the design discussion (not before the wrap-up):

(1) VISIBILITY, read-only and cheap: lanes' open asks flow into 'yaks inbox' (e.g. 'yaks inbox --lanes', or by default with a lane label), showing the question read from the lane's working tree.
(2) WHERE THE ANSWER LIVES. Today the human answers in his own checkout, the answer sits uncommitted there, and the coordinator reads it across checkouts by hand (a 'Yak herding.' commit later), so two copies of the yak diverge and the merge is noisy (O52 shows same-file edits conflict). Options:
	(a) keep it there and have lanes/inbox read the primary's working tree for answers addressed to a lane (no writes into other checkouts, but the asker must go and look);
	(b) write the answer into the ASKING lane's copy through yaks ('yaks answer <id> --lane <label>': one appended note, 'needs' cleared, left dirty there for the asker to commit with its own work); breaks the read-only-in-other-checkouts rule on purpose and risks a same-file conflict if the asker later writes the same yak (the team-mode skill avoids that today by having the asker run 'yaks answer' on the human's stated authority, so the yak keeps one writer);
	(c) a sidecar answer file: breaks one-file-per-yak.

My lean: (1) first, it is read-only; for (2) keep today's rule (one writer: the asker records the answer on the human's word) and make it frictionless by (a)-style visibility in both directions, deciding on (b) only after we have used (1).

Carried over from yaks-7eea (shorn 2026-10-10), for the TUI design:
- A shed picker in the TUI: open `yaks tui` in the main checkout, press a key, choose a shed, and the TUI re-roots to it. `--shed` has full write access, so show a banner naming the shed.
- Possibly an `open:` line / `--paths` in `yaks sheds` (a ready-to-paste cd and tui command), only if the picker leaves a need.
Semantics for the TUI to rely on are the 2026-10-10 Decisions on yaks-ee0a (one fork-point baseline per shed, working tree as the shed side, `cwd` irrelevant, per-yak state per shed).
