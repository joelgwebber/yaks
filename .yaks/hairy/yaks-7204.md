Joel (2026-10-04, on the lanes results): most lanes differ from the main checkout by a small delta, so the concept may layer into the UI more usefully than a top-level lane picker; ill-formed so far. Sketches to react to (coordinator's, not decisions): (a) a yak-centric view: for each yak, which lanes have changed it, as a badge in list/tree rows ('yaks-d738 ▸ lanes-2 shaving'); (b) a 'lanes' section in yaks show and in the TUI detail pane; (c) a conflict warning when two lanes have changed the same yak (the same-file conflicts of yaks-df61 O52 are exactly that); (d) lanes' open asks (needs:) flowing into inbox; (e) 'what would land' per lane = its delta against the base. All of it is read from the data layer in src/lanes.rs (yaks-e545/d738) behind a CLI form first. Needs a design conversation with Joel before any code.

▸ 2026-10-05T21:14:40Z [delta-lead]
Case from Joel (2026-10-05, yaks-36b6): an ask raised in a lane (here the coordinator's thread checkout) is invisible in the human's primary checkout: 'yaks inbox' there reads only that farm, so Joel could not see yaks-36b6 without digging into the worktree. 'yaks lanes' already shows '<id> needs: human' per lane but not the question text, and nothing writes an answer back. Two separate needs, to settle in the design discussion (not before the wrap-up):

(1) VISIBILITY, read-only and cheap: lanes' open asks flow into 'yaks inbox' (e.g. 'yaks inbox --lanes', or by default with a lane label), showing the question read from the lane's working tree.
(2) WHERE THE ANSWER LIVES. Today the human answers in his own checkout, the answer sits uncommitted there, and the coordinator reads it across checkouts by hand (a 'Yak herding.' commit later), so two copies of the yak diverge and the merge is noisy (O52 shows same-file edits conflict). Options:
	(a) keep it there and have lanes/inbox read the primary's working tree for answers addressed to a lane (no writes into other checkouts, but the asker must go and look);
	(b) write the answer into the ASKING lane's copy through yaks ('yaks answer <id> --lane <label>': one appended note, 'needs' cleared, left dirty there for the asker to commit with its own work); breaks the read-only-in-other-checkouts rule on purpose and risks a same-file conflict if the asker later writes the same yak (the team-mode skill avoids that today by having the asker run 'yaks answer' on the human's stated authority, so the yak keeps one writer);
	(c) a sidecar answer file: breaks one-file-per-yak.

My lean: (1) first, it is read-only; for (2) keep today's rule (one writer: the asker records the answer on the human's word) and make it frictionless by (a)-style visibility in both directions, deciding on (b) only after we have used (1).
