Goal (Joel's answers on yaks-7204, 2026-10-13):
1. Shed-only rows. A yak that exists ONLY in another shed (its `YakChange.added` and not landed, in a shed that is not the current one) appears on the yak views as a dim row with a `🛖` badge naming the shed, placed by the SHED copy's status and parent: under its parent when that parent exists here, else at the root of its status view. Call them "shed-only" rows in code: `tree::Row.ghost` already means something else (the dimmed ancestor context rows), do not reuse or rename it.
2. Data: the snapshot carries each shed-only yak's full `Task` from the shed's farm (title, status, parent, labels, body, needs), read once per scan in `Snapshot::scan` (read-only: `store::discover_with(&shed.path, None)` + `store::load`, as `sheds.rs` reads shed farms). Expose ONE query beside `copies`/`open_asks`: e.g. `Snapshot::shed_only() -> Vec<(&Shed, &Task)>`, the shed this TUI runs in left out. The same yak added in two sheds: one row, the first shed in attention order, and the conflict marker (4).
3. Read-only. A shed-only row's detail is the shed copy rendered with `detail::build`, under a banner line `only in shed <name>`; every yak-mutating key (S, E, P, T, L, D, R, H, M, A, X, c/C as child, m, *) refuses with the notification `<id> is only in shed <name>: read-only here` and changes nothing; `a` on it answers its ask in that shed when it is `needs: human` (reuse `open_answer_in_shed_prompt`), else refuses like the others. `y` copies the id.
4. Conflict marker. When two or more other sheds changed the same yak (outstanding in each: `copies(id).len() >= 2`, or a shed-only yak added in 2+ sheds), the row badge shows `⚠` (e.g. `🛖2⚠`) and the detail's `Sheds:` section opens with a line saying the yak was changed in N sheds.
5. The drawer chip `copies: any | home` (default `any`). `home` hides shed-only rows AND every badge and the detail Sheds section, for a plain view of this farm. Put it where the drawer's other chips live; if it needs a `FilterSpec` field (src/filter.rs) so saved views can hold it, add it with the default omitted when views are saved (old saved views load unchanged), and say how in a Decision note.

Scope: src/tui/sheds_tab.rs (scan + the new query + fixture variants), src/tui/viewmodel.rs (`rows`, `view_count`, `flat_rows`: the tasks the views build from), src/tui/tree.rs if placement needs it, src/tui/render.rs (`list_item` badge text), src/tui/detail.rs + detail_nav.rs (banner, conflict line), src/tui/handlers.rs (the read-only guard, `a`), src/tui/drawer.rs + src/filter.rs (the chip), tests anywhere under src/tui/ (central whole-frame ones at the end of src/tui/tests.rs). Decision: how shed-only tasks join the rows. The scan reads each shed's full `Task` once (`Snapshot::only_tasks`, parallel to `sheds`; `store::discover_with` + `store::load`, filtered to `YakChange.added && !landed`); `Snapshot::shed_only()` is the one query. The App unions them with `self.all` as a `Vec<&Task>` (`App::overlay_tasks`) and `tree::build_over` places them like any other yak, flagging the row `Row.shed_only` (a new field; `ghost` untouched). Rejected: a separate "in sheds only" group per view (loses tree context, Joel chose placement by shed status/parent); cloning shed tasks into `self.all` (would make them editable, countable, resolve dependencies, and leak into every `self.task(id)`). `tree::build` stays as the `&[Task]` wrapper (test-only now). Shed-only yaks never count as resolved dependencies (`resolved_ids_of` filters them). A yak this farm also has is never shed-only, whatever a stale snapshot says.

Decision: where the chip lives. A new drawer row `copies  any home` (last fixed row, `DRAWER_ROWS` 7 -> 8, the herd row moves to 9), a radio (Space on a chip sets it; `any` is the default) rather than a toggle. Backed by `FilterSpec.home_only: bool` so views and the live filter hold it. Rejected: a global key/toggle outside the drawer (not saved with views, not where Joel asked), putting it in the `deps` row (not a dependency predicate), a three-chip row with a separate "shed-only" setting (more states than the one rule needs).

Decision: `home_only` persistence. `views_store::spec_to_json` writes `"home_only": true` only when set (so a saved view that never used it is byte-identical); `spec_from_json` defaults it to false (old views load unchanged). `spec_eq` compares it, so the filter-modified marker appears. `filter::matches/apply` ignore it (it is not a task predicate); the CLI's `build_spec` sets false. `filter_summary` is unchanged (the chip is visible in the drawer).

Decision: one gate for the overlay. `App::overlay()` / `overlay_of(spec)` return the snapshot unless `copies: home`; shed rows, badges, the detail Sheds section, the Inbox's shed asks (`flat_matches`) and `a` on a row (`selected_shed_ask`) all read through it, so `home` is one rule, not five.

Decision: badge text. Shed-only row: `🛖<shed name>` (name truncated at 18), dim; a yak this farm has: `🛖N` as before; two or more sheds (changed, or added for a shed-only yak): `🛖N⚠`, shown in the warning yellow like an ask. Detail: a `⚠ changed in N sheds` warning line first in the `Sheds:` section when N >= 2. Rejected: `🛖<shed>+1` for shed-only in two sheds (the one rule `copies(id).len() >= 2` gives the marker everywhere). The row's badge is also what the yak's `🛖` spacing gives (`🛖 wt` on screen: the emoji is wide).

Decision: read-only guard is one function, `App::guard_shed_only`, run in `handle_key` before the per-focus key match, for `S E P T L D R H M A X C m * a` (and `r`, attachment rename, in the detail). It refuses with `<id> is only in shed <name>: read-only here`; `a` opens `open_answer_in_shed_prompt` when the shed copy is `needs: human`. `c` (new ROOT yak) is not an edit of the selected yak and still works; `y` copies the id; `d/u/j/k/Enter/h/l/f/v/#` are unaffected. Rejected: guarding inside each `open_*` (a dozen places, easy to miss one when a key is added).

Decision: detail. The shed copy renders with `detail::build` over `self.all` plus the shed-only tasks (so a shed-only parent/child link is not "(missing)") under an `only in shed <name>` banner (`detail::banner`, Kind::Warn) and a blank line.

Decision: tests/cli.rs `run_headless` now runs the fixture farm from a COPY under the temp dir (outside any git repository), one directory per call. Without it `headless_session`'s golden frame picked up the machine's real sheds (it ran inside this repo and showed yaks-3bcd as a shed-only row), which is exactly the behaviour added here. Not a snapshot change; the goldens are unchanged.
