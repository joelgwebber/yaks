Found while auditing upgrade guidance (yaks-ec00). Read from the code, not reproduced.

The schema gate (`store::schema_status`, `migration_refusal`) runs only in `Farm::open_root` (`code:src/farm.rs#L927-L947`). A `yaks tui` holds its `Farm` for its whole life. Its interval sync (yaks-f0db, `src/tui/farmsync.rs`) pulls, then `reload_preserving_selection` re-lists the farm without re-checking `.yaks/schema`.

So when another machine runs `yaks migrate` and syncs, an older TUI that is still running pulls the new layout and keeps writing in the old shape (paths, keys) until someone quits it. `yaks migrate --help` says "quit every running `yaks tui` first", but that only covers the machine doing the migration.

Fix sketch: after any sync or reload, re-check `schema_status`. On `Newer`, stop writing (read-only, or refuse every mutation) and show "farm is on schema N; upgrade yaks and restart". The CLI is safe because it re-opens the farm per command.

Evidence wanted: a farmsync test in which a second clone bumps `schema` and pushes; after the tick, a mutation in the first TUI is refused with that message.

Fixed in 7ed9402: `store::lock` refuses every write when `.yaks/schema` is newer than the binary (`newer_schema_refusal`), so a long-lived TUI can't write the old shape into a pulled migrated farm. After a sync (interval or `U`) the TUI shows `read-only: ...` naming the upgrade.

Evidence: `a_pulled_newer_schema_makes_the_tui_read_only` in `src/tui/farmsync.rs` (second clone bumps the schema and pushes; after the tick the notice shows and `transition` is refused, file untouched). Full `cargo test` green (862 unit + integration).
