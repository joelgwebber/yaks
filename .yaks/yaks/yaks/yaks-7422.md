Joel, 2026-10-13: a long-lived shed's `yaks changes` lists every yak it touched since it forked, landed or not, so a shed that is all landed still reads like a pile of work. `yaks sheds` already prunes its itemized lines to what is outstanding and counts the rest `(N landed)`; `changes` should group the same way, and offer a focus on in-progress work for humans and agents alike.

Design (delta-lead, within Joel's ask; say so in a Decision note if something does not hold up):
1. Default text output of `yaks changes [SHED]` (`sheds::render_changes`): the outstanding yaks first, in full as today (bracket words, each new note's first line, `needs:`), then the landed ones folded into ONE line after them: `  landed (N): yaks-aaaa, yaks-bbbb, ...` (ids only, wrapped at a sane width or truncated with `+K more`; your call, say which). Use the prep helper `sheds::split_landed` (already in src/sheds.rs, tested) for the order. A shed with nothing landed prints exactly as today; one with only landed yaks prints the `landed (N)` line where the list would be.
2. `--outstanding`: drop the landed ones entirely (no fold line).
3. `--status <S>` (repeatable, same values and parsing as the query commands' `--status`): keep only yaks whose SHED copy's status is one of them (`YakChange.status`), so `--status shaving` is "the work in progress there". Combines with `--outstanding` (AND).
4. `--json`: unchanged shape (one object per yak, `landed` field), but `--outstanding` / `--status` filter it too. Default `--json` still lists every yak, landed included (agents read `landed`).
5. Empty after filtering: one line saying so (e.g. `  nothing outstanding (12 landed)` / `  nothing in shaving`), never an empty output.

Scope: src/sheds.rs `render_changes` (and `changes_json` only if filtering happens there; prefer filtering the `Changes` before rendering, in one place), src/main.rs `Command::Changes` (the two flags, clap help on the command and flags), tests (src/sheds.rs `mod tests` and/or tests/ integration). Docs: docs/cli.md (`changes` row), README if it describes `changes`, the yaks skill's `yaks changes [SHED]` table row (.agents/skills/yaks/SKILL.md), and the coordinating skill's watch list line for `yaks changes` (.agents/skills/yaks-coordinating/SKILL.md) if it should mention the focus flags.

Out of scope: src/tui/ (fold-1), the CLI `yaks sheds` table, any change to which yaks are `landed`.

Evidence (fail first): unit/integration tests for (1) a shed with both kinds (outstanding block first, one fold line), (2) only landed, (3) none landed (byte-identical to before), (4) `--outstanding`, (5) `--status shaving` and its combination with `--outstanding`, (6) `--json` filtering, (7) the empty-after-filter line. Real machine: from Joel's checkout, `yaks -C /Users/joel/src/yaks changes sheds-tui-thin-sheds-tab` (the coordinator's shed, all landed today) before and after, pasted; and `--status shaving` on it. ▸ 2026-10-13T20:00:55Z [changes-1]

Decision: fold line format is `  landed (N): id, id, ...` (ids only), wrapped at 100 columns with a 4-space continuation indent, never truncated with `+K more`. Rejected: truncation (hides which yaks landed; the list is the only place they are named now) and one id per line (defeats the fold).

Decision: filtering lives in one new type, `sheds::Focus { outstanding, statuses }`, applied to the `Changes` yaks before rendering, in `render_changes_with` and `changes_json_with` (`render_changes`/`changes_json` stay as the no-focus wrappers, so existing callers and tests are untouched). Rejected: filtering in main.rs (two copies) and mutating `Changes` in place.

Decision: `--status` is the shed copy's status (`YakChange.status`), repeatable, parsed with the existing `parse_status` values via a new `parse_statuses` in main.rs that ERRORS on an unknown value. The query commands silently drop an unknown status (filter_map), which for `changes` would show every yak while looking filtered. Rejected: copying the silent drop.

Decision: flags are `--outstanding` (bool) and `--status`, as the claim named; no short forms. Rejected: `--landed`/`--no-landed` and a `--fold` toggle (no ask).

Decision: the `, landed` bracket tag is gone from the text view (a landed yak is no longer itemized, so the tag could never print); JSON `landed` is unchanged. The old test changes_marks_a_landed_yak_text_and_json now asserts the fold line. Docs/help no longer mention `, landed`.

Decision: the empty-after-filter line names the filters: `nothing outstanding (N landed)` (N = landed yaks left after any --status), `nothing in shaving`, `nothing outstanding in shaving, hairy`. A shed with no changes at all keeps its own `no changes of its own` / `no differences` wording regardless of flags.

Decision: `--status` is applied BEFORE the landed split, so `--status shaving` still folds the landed yaks that are in shaving (shows `landed (3): ...`), and `--outstanding` is what drops them; that is the AND the claim asks for. Seen on Joel's checkout below.
