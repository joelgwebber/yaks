Decided by Joel (2026-10-06/07, in the notes of yaks-ee0a), not built except `landed` (yaks-ed5e): a shed has one state from a small vocabulary: active, idle, landed, stale, orphan. "Its claim disagrees with the primary" (its own copy of a yak is `shaving` while ours is `shorn`) is a SIDE NOTE on the row, not a state. Liveness starts as the simplest signal: no farm activity for N hours while its own yak is still `shaving`; revisit only if it misleads. The tools never remove or clean up a shed: they name what is safe and may print the command.

Goal: define each state precisely (inputs: commits ahead/behind, dirty count, farm activity time, whether its changes are all in this checkout, whether its git dir or checkout is gone), show it in `yaks sheds` (text and JSON) and `yaks changes`, and record the definitions as Decisions. Design first with Joel; the TUI badges (yaks-7204) consume this.

Real-machine cases to define against (2026-10-10, ~/src/j15r): two clones with identical HEAD and identical uncommitted farm files, whose yaks are all further along in the primary (shorn there, `shaving` in the shed): that is `stale`, not outstanding work (see the note on yaks-ed5e). A pinned clone whose git dir is gone is `orphan`-adjacent (a finished thread).

Design question for Joel before any code (per this yak's own instruction). `yaks-ed5e` is in progress and resolves `landed` as: every yak the shed changed (relative to its own fork point) is already captured in the reference farm (the primary's live farm, else `origin/main`) — this covers both "exactly landed" and "superseded by the reference" in one check.

**The tension.** The original decision (2026-10-07) lists `active, idle, landed, stale, orphan` as ONE mutually exclusive vocabulary. But the real-machine case written into THIS yak ("two clones with identical HEAD and identical uncommitted farm files, whose yaks are all further along in the primary... that is `stale`, not outstanding work") describes exactly the SUPERSEDED case that `yaks-ed5e` now calls `landed`. So either the case note used "stale" loosely before the vocabulary was pinned down, or `stale` and `landed` are meant to overlap on purpose. I don't think they should mean the same thing, but there are a few ways to split them. Options:

**A. Liveness and landedness are orthogonal — two fields, not one enum.** `landed: bool/count` (from `yaks-ed5e`) answers "is anything outstanding". A separate liveness signal (`active`/`idle`/`stale`) answers "is anyone still touching it" and applies regardless of landed-ness. A shed can be landed-and-idle (the common case: it's done, nobody's touched it since), landed-and-stale would be unusual (its own idea of "shaving" disagrees with the reference's "shorn", but there's genuinely nothing outstanding — your real-machine case fits this), or outstanding-and-active (real work in flight) or outstanding-and-stale (abandoned mid-work — the case the original liveness heuristic was written for). `orphan` stays a third, separate bit (pin resolves to a gone git dir — can't even read it). This keeps `landed` exactly as `yaks-ed5e` ships it and adds liveness beside it, not instead of it.

**B. One priority-ordered enum, `landed` wins over the liveness states.** `orphan` > `landed` > `active` > `stale` > `idle`. A shed with real outstanding work and recent activity is `active`; with outstanding work and no activity for N hours it's `stale`; with nothing outstanding at all it's `landed` regardless of activity (so your real-machine case reads `landed`, not `stale`, despite the literal wording in the earlier note). This keeps one word per shed (simpler to render as a single badge) but means the earlier case note's wording was imprecise and should be corrected, not taken as the definition.

**C. Keep `stale` as liveness-only (matches the 2026-10-06/07 decision text exactly: "no farm activity for N hours while its own yak is still shaving"), and fix the case note's wording instead of the vocabulary.** The two "stale" j15r clones would be `landed` (ed5e) and ALSO flagged stale by liveness if nobody's touched them in N hours — same outcome as A, phrased as "the note used the wrong word, not that two concepts collapse."

My lean: A. It keeps `yaks-ed5e`'s landed exactly as specified (nothing to redo there), and a one-enum design (B) would have to special-case "landed but also been idle forever" vs "landed and just finished a minute ago" if that distinction ever matters — A keeps that open for free. C is really the same resolution as A with a different enum shape; I'd rather not force one combined enum if the two questions ("anything outstanding" and "is it alive") already have clean independent answers.

Also open: the liveness THRESHOLD (what counts as "no activity for N hours" — a fixed default, configurable, or derived from something else), and whether `orphan` is detected here (git dir gone) or already fully covered by `yaks discover`'s existing "gone" reporting and this yak only needs to surface it on the `sheds` row.

Design (coordinator, decision A confirmed): liveness is a small state orthogonal to `landed` (yaks-ed5e, shipped). Proceeding without a further round, per "let's plow ahead" — recording the remaining calls as Decisions for review rather than asking again.

## Liveness: `active` / `idle` / `stale`
Computed uniformly for every shed INCLUDING the primary (unlike `landed`, this is not a comparison to anything, so there is nothing vacuous about applying it to yourself):
- `stale`: `in_progress` is non-empty (it has claimed a yak and left notes there, exactly the existing `label()` signal) AND `farm_activity`'s raw mtime is more than a threshold old. Default threshold: 2 hours (`STALE_AFTER`), named and documented, not configurable yet — record as a Decision; a config override is a natural follow-up if 2h misleads in practice (the original decision's own words: "revisit only if it misleads").
- `active`: `in_progress` non-empty and NOT stale (recent activity).
- `idle`: everything else (no claim at all, or a claim whose activity cannot be told — `farm_activity` unknown/`None` counts as idle, not stale: no signal is not evidence of abandonment).

`farm_activity` is already computed as a formatted string (`newest_mtime`/`format_time` in `inspect()`); keep the raw `SystemTime` alongside long enough to compare against `SystemTime::now() - Duration::from_secs(2*3600)` before formatting it away.

Render: silent for `idle` (the common case; no new noise). `active`/`stale` show as a short tag — put it on the label line (`label_line`, beside `who:`/`shaving:`) so it reads naturally: `who: land-1 · shaving: yaks-ed5e · active` / `· stale`. JSON: always present, `"liveness": "active"|"idle"|"stale"` (string, consistent with `kind`/`vs`), on every shed object including the primary's.

## Orphan: NOT folded into `Shed`
A gone Delta pin (`Pinned.checkout: Err("gone...")`, already detected in `pinned()` and already shown by `yaks discover`) has no checkout path at all — `checkout_paths` drops it today because there is nothing to key a `Shed` row by (no git state, no farm, no `ahead`/`behind`). Forcing it into `Shed` means making `path` optional and auditing every consumer (`resolve`, every render column, farm-root derivation) for a row that cannot really act like the others. Decision: keep `orphan` OUT of `Shed` and the stable `sheds --json` array (still exactly "real checkouts you could act on"); instead `yaks sheds`'s TEXT output gets one extra informational section, reusing `pinned()`'s existing gone list (the same data `yaks discover`'s PINS section already shows): e.g.
```
orphaned (1): a pinned clone whose git dir is gone (a finished thread)
  47g751xth9ea
```
No JSON array for this yet (nothing new to query that `yaks discover --json`'s `pins[]` doesn't already give you); if that turns out to be wanted, it is a small, separate follow-up, not blocking this one.

## Scope
`src/sheds.rs` (the `Liveness` enum, the field on `Shed`, computing it in `inspect()` alongside `farm_activity`, the label-line render, `to_json`, the orphaned-pins text footer in `render`, tests). Docs: `docs/cli.md`, `README.md`, `.agents/skills/yaks/SKILL.md` (the `sheds` row, next to `edited`/`landed`). `--help` text in `src/main.rs` if it lists the rules.

Out of scope: TUI badges (yaks-7204, later), `yaks changes` (liveness is a per-SHED property, not per-yak — `changes` stays as is), any JSON array for orphans, a configurable threshold (hardcode 2h, document it, leave the override as a follow-up).

## Evidence (tests FAIL first)
- A shed with a claimed yak and recent `farm_activity`: `active`.
- A shed with a claimed yak and `farm_activity` older than the threshold: `stale`.
- A shed with no claim, or unknown `farm_activity`: `idle`.
- A shed that is fully `landed` (yaks-ed5e) AND stale (no activity): both signals present at once, independently (the real j15r case from this yak's own notes).
- The primary's own row gets a liveness value (unlike `landed`, which it never gets).
- `yaks sheds` lists an `orphaned` footer for a gone pin (fixture: a pin whose git dir has been removed), and the normal table is unaffected when there are none.

Decision: render()'s signature gains an `orphaned: &[Pinned]` parameter (the spec said the footer belongs "in render()"). The alternative was a separate `render_orphaned()` function the caller concatenates, which would have avoided touching ~35 existing `render(&sheds)` call sites in tests -- rejected because the spec is explicit about where the footer lives, and the mechanical signature-update (scripted literal substitution, confirmed by `cargo build --release`) is low-risk.

Decision: `orphaned_pins()`'s filter is "any `Pinned` whose `checkout` is `Err(_)`", not specifically the "gone (its git dir no longer exists)" string. `resolve_pin` has three other Err reasons (no core.worktree, checkout dir missing, no clone store known) that are not literally "a gone git dir", but the spec's own text ("reusing pinned()'s existing gone list ... the same data yaks discover's PINS section already shows") describes discover's PINS section, which shows EVERY Err entry with its own reason regardless of which one -- so one rule (any resolution failure) beats special-casing the exact wording of one reason.

Decision: the orphaned footer's exact text ("orphaned (N): a pinned clone whose checkout could not be resolved (most often a gone git dir -- a finished thread)" then one "<dir>/<name>: <reason>" line per pin) is my own wording, not a literal copy of the yak's "e.g." illustration (which showed only a bare dir id with no name or reason). I added `<name>` and the specific error text because discover's own PINS section already shows both, and a reviewer debugging a real gone pin benefits from the reason without a second `yaks discover` run.

Decision: the liveness-ages-out test backdates files with `std::fs::File::open(path).set_modified(t)` (stable std since 1.75) rather than adding the `filetime` crate as a direct dependency -- Cargo.toml edits are forbidden for this yak, and `filetime` is only a transitive dependency today (pulled in by `notify`), not something this crate can `use` without declaring it itself.
