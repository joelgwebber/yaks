Initial thoughts and observations:

The first child (yaks-bede) captures the fact that simple links don't work properly for sessions and sources. Clearly we need to be sure what layout we want before we can resolve the rest.

I'm also finding it useful to browse them directly in Github. Its markdown rendering is decent, and handles most of these files pretty well. Eg, [this yak](https://github.com/cowpaths/joel/blob/yaks/.yaks/joel/yaks/joel-ec9c.md) renders quite clearly, as does [this dok](https://github.com/cowpaths/joel/blob/yaks/.yaks/doks/topics/itau-perf-investigation.md), but the former tries to link to the latter at `/cowpaths/joel/blob/yaks/doks/topics/itau-perf-investigation.md`, presumably because of the missing `.yaks` at the root.

If we can ensure that our file structure and naming scheme is coherent, then these things should all "just work" on direct Github links, which would super-useful for sharing, especially for readers not actually using `yaks` directly. We might even consider a simple affordance for opening the current yak/dok/etc in Github (extensible to other hosting platforms without too much difficulty), for quick sharing.

Short version: dropping `.yaks/` lifts authored links that work on GitHub from 51% to 74% with no rewrites; the rest is yak-id links (453), `code:` links and note anchors, which need a stored-form change, so layout and link rewrite ship as one schema-9 migration. Questions, my lean first:

1. **Drop the `.yaks/` root**, branch root becomes the farm root, plus a static `README.md` landing page and a stub `.yaks/schema` so old binaries get the "upgrade" refusal rather than "restore .yaks/". Lean: yes.

3. **Keep the no-`../` rule** from yaks-ccb1 (GitHub lets `../` escape the repo, GitLab and Gitea stop at the root). Lean: keep.
4. **Pinned `code:` links stored as host URLs** (`https://github.com/o/r/blob/<sha>/path#L12`), parsed back to code links by yaks; unpinned `code:` unchanged. Lean: yes. Cost: the stored text names the host.
5. **Note anchors:** defer. GitHub gives a note no anchor, and the fix changes the note format. A note link on GitHub lands on the yak. Lean: defer and file a yak.
6. **Do not shard the yaks directory** now (GitHub truncates listings at 1000 entries, this farm has 881), accepting a later migration if it is ever needed. The alternative is sharding by id prefix in this same migration, the cheap moment. Lean: don't shard.
7. **Fan-out:** may I file the work yaks (resolver and `yaks url`, the TUI `O` menu, layout, schema-9 migration, docs) and start the two layout-independent pieces (A and B in the dok) with Sonnet workers?
