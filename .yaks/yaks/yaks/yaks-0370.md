It looks like we currently only render inline images in yaks/docs, if they're in their own block/paragraph. So a line like this doesn't render anything but the link:

`Here's an image: ![some image](some-image.png)`

At the very least we should render these on their own line if they're at the end of the block. But also fine to just render them regardless, splitting up the text block. I don't see any obvious reason to get wacky with text wrapping and other complex layout strategies.

Done in the working tree (not committed: awaiting a go-ahead to land).

## What changed

- An image in a top-level paragraph is now drawn under that paragraph whether or not it is the whole paragraph (`Here's an image: ![some image](...)`). The text is not split; the `🖼 alt` link row stays followable.
- Several images in one paragraph are drawn one after another, in order.
- Unchanged: an image in a list, quote, table or footnote stays the link row; remote, svg, missing or undecodable images stay the link row; `inline_images: false` still turns it all off.
- The rule is `MdImage::top_level` (was `alone`), set for every image of a top-level paragraph in [fn mark_top_level_images](code:src/tui/mdrender.rs#L606-L618); [fn md_rows](code:src/tui/detail.rs#L597-L641) now queues all of a paragraph's slots instead of the first.

## Evidence

- New test `an_image_among_text_is_drawn_under_its_paragraph`: three placements (end, middle, start of the text) each reserve 6 rows right after the paragraph and draw 6 pixel rows; two images in one paragraph reserve 12.
- Updated: `an_image_in_a_top_level_paragraph_is_flagged`, `image_size_token_is_hidden_and_carried_on_the_row` (their old expectations were the removed rule).
- `cargo test`: all pass (948 unit tests).
- Headless frame of the yak's own example: `Here's an image: 🖼 some image`, six reserved rows, then `After that paragraph.` The picture itself does not show in a text frame.
- Docs and help: `docs/tui.md` (Inline images), `README.md` (`inline_images`), the `?` overlay row in `src/tui/keymap.rs`, and the `inline_images` doc comments.

## Not done

- The `tui-image-inline.svg` docshot still shows the lone-image case, which is still correct; I did not add a mixed-text scene.

▸ 2026-11-04T00:23:14Z [indent-links]

Re Joel's caption question: what CommonMark offers, and what yaks does today.

## What the markdown dialects have

- **No caption syntax** in CommonMark or GFM. The usual stand-ins are an italic line under the image, HTML `<figure>`/`<figcaption>`, or the image **title**.
- **Image title**, `![alt](src "Caption")`, is the one standard slot. GitHub and most viewers show it only as a hover tooltip, so it degrades quietly: the image still shows and nothing stray appears.
- **Alt text** is for accessibility and the broken-image fallback, not a visible caption. In yaks it also carries the `=50%` size token (`![shot =50%](...)`), so it is already doing a second job.
- **HTML** (`<figure>`) is not rendered by yaks: inline HTML shows as literal text.

## What yaks does today

- The title is parsed and thrown away: `Tag::Image { dest_url, .. }` in [the renderer](code:src/tui/mdrender.rs#L507) never reads it.
- The `🖼 alt` link row is the only visible text for an image, so alt is the de facto caption.
- A `Context: ![..](..)` paragraph now draws its picture under the paragraph (this yak's fix), so the label sits above the image, not beside it.

## Lean

Render the image **title as a caption line directly under the picture** (dim, wrapped to the pane), and teach agents to write `![alt](src "Caption")`:

- It is standard markdown, so it is portable and degrades to a tooltip elsewhere.
- It replaces the `Context:` lead-in with something attached to the image rather than a paragraph above it.
- Alt stays short and plain, and the size token stays where it is.

Open points for the human: show the title when the image is not drawn (link row only, so a caption would sit under a single row), and whether `yaks attach` gets a `--caption` that writes the title.

Not started. The base fix on this yak is independent and does not depend on it.

▸ 2026-11-04T00:42:24Z [indent-links]

Decision: captions are the image's markdown **title**, built on top of the inline-image fix above (same working tree, not committed). Joel's answers to the two open points:

- A caption shows whenever the picture is not drawn (remote, missing or undecodable file, `inline_images` off), under the `🖼 alt` link row.
- `yaks attach` gets `--caption`.
- Remote images stay undrawn on purpose (local copies do not break); SVG is drawn like any other image.

## What changed

- **Caption:** `MdImage::caption` reads the title (whitespace collapsed, blank is none). [fn md_rows](code:src/tui/detail.rs#L597) puts it on the rows after the picture, or after the link row when nothing is drawn: dim italic ([fn caption](code:src/tui/palette.rs#L75)), wrapped to the pane, in the paragraph's own source block. Only a top-level paragraph's images get one; a list, quote or table image stays a bare link row.
- **SVG:** drawn in place. Its size has no file header, so [fn image_dims](code:src/tui/detail.rs#L718) takes it from the cached rasterization (the same PNG cache the viewer uses), once per content. A malformed svg stays the link row.
- **`yaks attach --caption "..."`:** writes `![name](<id>/<file> "...")` through one link builder, `store::attachment_link_titled` (quotes and backslashes escaped, line breaks become spaces). It refuses several files and `--no-link`, since the caption belongs to the one image it links.
- **Guidance:** the `yaks` skill (caption it, prefer it to a `Context: ![..](..)` lead-in, keep images local), `src/brief.rs`, the `attach` clap help, `docs/cli.md`, `docs/tui.md` (Inline images, Image captions) and the `?` overlay row.

## Evidence

- New tests: `an_image_title_is_its_caption` (parsing), `attachment_link_titled_writes_an_escaped_title`, `an_image_title_is_a_caption_under_the_picture` (drawn, not drawn, remote, missing, `inline_images` off, wrapped, several images, list), `an_svg_attachment_is_drawn_in_place` (and a malformed svg).
- `cargo test`: all pass (952 unit tests).
- Scratch farm, my binary: `yaks attach T shot.png --caption 'The login page, on mobile'` and the same for an svg; `doctor` is clean; the headless frame shows `🖼 shot`, six rows, then `The login page, on mobile`, then `🖼 d`, the svg's rows, then `An svg diagram`. `--caption` with two files or with `--no-link` exits 1 with a message.

## Not done

- No docshot scene for a caption or a mixed-text paragraph; the existing image docshots are still accurate for what they show.
