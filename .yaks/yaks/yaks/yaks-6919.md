Key collisions for phase 7: one meaning per key. Free letters today are `F`, `I`, `Y`, `Z`, `b`, `e`, `s`, `t`, `w`, `x`, `z` and most Ctrl chords. For each, my lean first; reply per number (or "all leans").

1. **`h`:** family scope in a list, back in the pane.
   - Lean: `h` is back/left everywhere (in a tree list, collapse or go to the parent, like a file manager), and the family scope moves to `F`.
   - Alternative: keep it as is.
2. **`v`:** view picker in a list, visual select in the pane.
   - Lean: `v` is visual select everywhere (vim), and the view picker moves to `` ` `` (or `;`).
   - Alternative: keep `v` for views, and visual select moves to `V`, displacing save-view to `Ctrl-S`.
3. **`N`:** new page on the Wiki, previous match in the pane.
   - Lean: `N` is previous match everywhere; a new page is `c` on the Wiki view (`c` means "create the row kind of this view": a yak on yak views, a page on Wiki).
4. **`r`:** rename attachment in the pane, reread on Wiki, rescan on Sheds.
   - Lean: `r` is rename; refresh becomes `Ctrl-R` everywhere (rarely needed, since both refresh themselves).
5. **`q`:** quits from a list, closes the viewer.
   - Lean: `q` always quits; `Esc`/`h` close or go back. Once the viewer is part of the pane (phase 4), a `q` that sometimes closes and sometimes quits is the trap.
6. **`Tab`, `[`, `]`:** next view in a list, next link in the pane.
   - Lean: keep. Focus makes the difference obvious, and both are "next thing at this level".
7. **`o`/`i`:** back/forward, once phase 5 makes them global.
   - Lean: keep, and add `Ctrl-O`/`Ctrl-I`-free aliases only if asked.
8. **which-key:**
   - Lean: a popup listing the current context's commands after a 600 ms pause on a prefix key; no leader key until something needs a second layer.
9. **User overrides:**
   - Lean: a `keys:` map in the user config (`~/.config/yaks/config.yaml`, never the farm), by command name (`view.next: ["Tab", "]"]`); editor keys stay with edtui's vim and emacs modes.

Decision: which-key is option A (as the coordinator said): `?` opens `Overlay::Keys`, a bottom popup of the current context's bindings (`Keymap::popup_entries`, from the table); `?` again (the effective `app.help` key) opens the full reference; any other key closes it and is not run.

▸ 2026-11-03T06:07:01Z [keys-2]

Decision: overrides (`src/tui/keymap/overrides.rs`, `Keymap::from_config`/`load_user`).
- An override replaces the command's keys in every context it is bound in (spec). A list with some bad keys keeps the good ones; all bad, or `[]`, or a blank value: reported, override ignored. Rejected: `[]` as "unbind" (a blank value would silently unbind); left as a follow-up.
- An override that gives two commands one key in a context is dropped whole and reported. The test is "same context and the rows overlap" (same kind, or one is for any kind), stricter than the table's own test, because a kind's binding shadows a general one and a shadowed override would silently not work. Rejected: let the override win and strip the key from the other command (hides a command from `?`), and last-wins (`?` would lie).
- Two commands may trade keys (`move.down: [k]`, `move.up: [j]`): the check runs after all overrides are applied.
- Reported once, as one notification at startup (first two reasons then `+N more`, since it is one line). Rejected: stderr (the alternate screen eats it).
- Key strings are `Key::label` forms, parsed by `Key::parse` (a test round-trips every key in the table); I also accept `Up`/`Down`/`Left`/`Right` for the arrows, which are hard to type in YAML.
