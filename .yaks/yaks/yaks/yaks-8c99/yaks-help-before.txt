Filesystem-native task tracker (Rust)

Usage: yaks [OPTIONS] <COMMAND>

Commands:
  list               List tasks (non-dead by default; --all also includes dead)
  show               Show one task by id. With `--sheds`, also show how the OTHER checkouts of this repository (git worktrees, Delta clones; not the one you are in) have that yak: this checkout's copy first, then one block per shed whose copy differs (its status, `needs:`, and the note entries it has that this copy lacks) and one line counting the sheds that are the same, lack the yak, or have no farm of their own. Works for a yak that exists only in a shed (plain `show` still exits 1). Read-only in the other checkouts
  path               Print the current on-disk file path of yaks, one per line: by id (`yaks path yaks-1a2b ...`) or by the shared filter flags (`yaks path --status shorn --label cli`). Each yak's file is `.yaks/<herd>/yaks/<id>.md`, the same path for its whole life (a status move edits it in place), handy for `git add`. Paths are absolute. An unknown id is reported on stderr and the exit status is non-zero (known ids are still printed). Give ids or filter flags, not both. With neither, print the farm root this command resolved (the farm branch's worktree when the farm is a branch): which farm am I on?
  refs               List the yaks a task points at (parent, deps, and id mentions in its text), flagging any formal reference that dangles. With --incoming, list the yaks that point at it instead
  commits            Show the git commits linked to a yak: those naming its id and those that touched its file across status moves
  verify             Run a yak's recorded `verify:` command and record the PASS/FAIL as an attributed evidence note. Explicit — yaks never auto-runs it. Exits non-zero if any verify fails (or a yak has no `verify:` command)
  attach             Attach a local file to a yak as evidence: copy it under `.yaks/<herd>/yaks/<id>/` (beside the yak's file) and link it in the body as `![name](<id>/<file>)` for an image (png, jpg, jpeg, gif, webp, svg) or `[name](<id>/<file>)` for any other file. Use for artifact evidence a human or coordinator can look at (screenshots, TUI frames)
  rename-attachment  Rename a yak's attachment in `.yaks/<herd>/yaks/<id>/` and rewrite every link to it across the farm (the link text follows the new stem, and the `!` of an image link follows the new extension). NEW is sanitized and keeps OLD's extension if it omits one; refuses to overwrite an existing attachment
  attachment         Find a yak's attachments wherever they are: this checkout's farm first, then every other shed's (git worktrees, Delta clones), so evidence a worker attached in its shed is readable before it lands. With no FILE, lists each attachment as `<shed>  <absolute path>` (`.` = this checkout; a name this checkout has hides other sheds' copies). With FILE, prints that one's absolute path, or exits 1 when no farm has it. Read-only
  scan-ids           Scan text for tokens that are real yak-ids in this farm — a leak check for private-mode farms (pre-commit / PR hook). Reads a FILE and/or stdin, prints each found id as `line:col  id`, and EXITS NON-ZERO if any are found (clean text exits zero)
  next               List hairy tasks whose dependencies are all resolved [alias: ready]
  tangled            List hairy tasks with at least one unresolved dependency [alias: blocked]
  log                Timestamped notes and status moves across a filtered set, oldest first (an activity log)
  search             Substring search over id/title/description
  sheds              List EVERY checkout of this repo (git worktrees and Delta clones), the one you are in included: it is marked (a `*` in the first column and `(here)` on its `name:` line, JSON `current: true`, `false` on every other row) and measured like any other, so where you run this only picks which row is marked, never an answer. Each row says what that checkout's farm CHANGED since the shed forked (the oldest entry of its HEAD reflog, so a worker is not credited with what its coordinator did first, or the target of a later switch onto the branch it is on now unless that switch branched off its own commits; the same from every checkout, so what the shed merged in since counts as its own): yaks only there, yaks in another status, new notes, `needs:` set, yaks edited (title, fields or description, as `yaks status` reads them), and yaks `landed` (already in the REFERENCE farm — the primary's own live farm when visible and readable, else this checkout's branch upstream: all touched landed replaces the summary with `landed (N yak)`; some landed adds `(K landed)` and prunes the itemized lines to what's still outstanding; never set for the primary's own row; JSON `farm.landed`, an array of ids). The PRIMARY checkout is measured from the UPSTREAM of its branch instead (`@{upstream}`, else `origin/<branch>`, else `origin/main` / `origin/HEAD`'s target) against its working tree, i.e. what it has not published, and names the ref, e.g. `(vs origin/kinds-discovery)`, JSON `farm.upstream`; with no usable ref it falls back to its fork point and says `(vs fork)`. With no usable reflog the baseline of any other shed is the merge-base with this checkout (the one case that depends on where you run it) and the output says `(vs merge-base)` (JSON `farm.vs`: `upstream`, `fork`, `merge-base` or `checkout`). Also how far ahead/behind its HEAD is of this checkout's (`+? -?`, JSON null, when there is no merge-base here, e.g. shallow history; the table then says once to `git fetch --unshallow`). A shed that is merely behind shows no changes. Each shed with entries of its own is labeled under its row: `who:` (the distinct actors on those new notes) and `shaving:` (yaks in shaving there that it wrote to); JSON `who` and `in_progress`. The same row also gets a liveness tag, computed the same way for every shed including the primary (not a comparison, unlike `landed`): `active` when it has a claim (`in_progress` non-empty) and farm activity within the last 2 hours, `stale` when that claim has had no farm activity for longer (unknown activity counts as `idle`, never `stale`), else `idle`; `idle` is silent (the common case), `active`/`stale` show on the label line, e.g. `shaving: yaks-d738 · stale`; JSON `liveness`, always present. A `state:` line says what keeps a shed around: `merged, nothing outstanding` (its HEAD is in the primary's history, nothing outstanding, a clean tree) or `uncommitted: N modified, M untracked` (JSON `merged`, `untracked`). A pinned Delta clone whose checkout could not be resolved (most often a gone git dir: a finished thread) is not a row here — there is no checkout to measure — but is listed in one extra text-only `orphaned` footer (no JSON array for this yet). A shed's name (the `name:` line, JSON `name`) is `main` for the primary checkout, else the slug of its Delta thread title (lowercase, other runs become `-`, at most 24 chars; the title is recorded in the clone's own git config by any yaks command run there with `DELTA_THREAD_TITLE` set, shown as `title:`, JSON `title`), else its first actor, Delta dir id or branch. Read-only everywhere (apart from that one-time recording in the clone you run yaks in)
  changes            What ONE shed (a checkout of this repo, picked like the rows of `yaks sheds`; with no SHED, the one you are in) created, moved and noted since it forked, per yak, with actors: new yaks (title, status), yaks in another status (from -> to), each new note entry (timestamp, actor, first line), `needs:` newly set, an `edited` yak (title, fields or description rewritten, as `yaks status` reads it; `updated:` alone is not an edit), and a `landed` yak (already in the reference farm, see `yaks sheds`; folded into one `landed (N)` line after the outstanding yaks). The per-yak expansion of the `farm:` line of `yaks sheds`, with the same baseline (the shed's fork point; the primary's branch upstream, else its fork point, `(vs origin/<branch>)` / `(vs fork)`; else the merge-base / this checkout, `(vs merge-base)` / `(vs this checkout)`). SHED is its path, Delta dir id, thread-title slug, branch or an actor on its notes, or a unique substring of those (or of its full title); `main` names the primary checkout whether or not you are in it, and your own shed works. No or an ambiguous match lists the sheds and exits 1. A shed sharing this farm, or with none or an unreadable one, says why there is nothing to show. Read-only everywhere
  discover           Diagnostic: show the chain `yaks sheds` uses to find the other checkouts of this repo, step by step, from inside any checkout of it: `git worktree list` here; the HOST repo this checkout's `objects/info/alternates` names (the human's checkout, or Delta's managed bare repo on a machine the thread was shared to); every `refs/delta/<dir>/<name>/*` pin group there, resolved to a live checkout through the clone's git dir `core.worktree` (or reported gone); and, when the host is a checkout, its own `git worktree list`. Git data only: nothing is searched for. Read-only; needs no farm
  stats              Show task statistics
  create             Create a new task (in hairy)
  update             Update fields, labels, or append a timestamped note. Accepts multiple ids; the same edit is applied to each
  ask                Block a yak on a human decision and record the question. Sets the `needs` field so the yak drops out of `next`; `answer` hands it to an agent (`needs: agent`) and `pickup` clears that. Asking a yak that is already answered (`needs: agent`) flips it back to `human`
  answer             Answer a question: record the reply and set `needs: agent`, so the yak shows in `inbox` (and, if hairy, `next`) as answered and awaiting an agent. The human-reserved counterpart to `ask`. `--done` clears `needs` instead, for an answer that needs no follow-up. A second answer keeps `needs: agent` and appends the note; on a yak with no `needs` it only records the note. `<id>@<shed>` answers in ANOTHER checkout's copy of the yak (a shed from `yaks sheds`; see `yaks changes`; your own shed is a plain `answer`): the reply is written into that working tree and left uncommitted there, for its worker to commit with its own yak file. The only command that writes outside this checkout
  pickup             Pick up an answered yak: clear `needs: agent` and record who took the work on (a `picked up` note). The only command that clears it; errors on a yak that is not `needs: agent`
  inbox              List yaks with a `needs` value, across all statuses, in two sections: awaiting a human (`needs: human`; `replied` marks one whose latest note after the ask is by someone other than the asker) and answered, awaiting an agent (`needs: agent`). `--for human|agent` shows one section
  shave              Start shaving one or more yaks (move to shaving) [alias: work]
  shorn              Mark one or more yaks shorn (move to shorn) [alias: close]
  regrow             Regrow one or more shorn yaks (move back to hairy) [alias: reopen]
  slaughter          Slaughter one or more yaks (move to dead)
  revive             Revive one or more dead yaks (move back to hairy)
  dep                Add or remove a dependency
  reparent           Move one or more tasks under a new parent (--parent) or to top-level (--unparent). Every id is reparented to the same destination
  bulk               Apply the same field edit (and/or reparent) to every yak matching a filter. DRY-RUN BY DEFAULT: without --commit it only prints the matched set and the mutation, changing nothing. Requires at least one filter flag (never operates on the whole farm) and at least one mutation flag. Field edits + reparent only — no state transitions (see yaks-7cc8)
  rename             Rename a yak, updating its file + id and every reference to it (parent, depends_on, and body/title mentions) across the farm
  rename-herd        Rename a whole herd: migrate every yak from one id prefix to another (e.g. yaksrs -> yaks), rewriting all references and updating the farm's configured herd. (`rename-prefix` still works as an alias.)
  migrate            Bring a farm on an older schema up to this yaks' (schema 4 or 5 -> 6): move every yak file and attachment dir from the farm root into its herd's directory (`<herd>/yaks/<id>.md`, `<herd>/yaks/<id>/`), put the blank line after every comment's `▸ <ts> [actor]` header, and link non-image attachments as `[stem](<id>/<file>)` instead of `![stem](<id>/<file>)`. Works under the farm lock, then sets `.yaks/schema` to 6. Idempotent: a current farm reports "nothing to migrate". Every other command refuses an older farm and names this one. Never commits: it prints the commit to make (a migration touches nearly every yak file, so land it on its own). Quit every running `yaks tui` first
  private            Mark this repository's farm private: it never leaves the machine through yaks or a stray `git push`. Sets `git config yaks.private true` and installs a `pre-push` hook (in the hooks dir `git` uses, so `core.hooksPath` is honored and every worktree shares it) that refuses a push of the farm branch (`yaks`, or `git config yaks.branch`), including `git push --all`; `yaks sync` commits and pulls but never pushes it. Pushing any other branch is unaffected. An existing `pre-push` hook that is not yaks's is left untouched (the command says how to chain the check)
  merge              Merge another farm's yaks into this one (consolidation). Copies every yak (all statuses) and its artifacts, preserving ids and status, and declares any incoming herd in this farm's config; refuses on id collisions. Non-destructive — the source is left intact
  init               Create a .yaks/ farm in the current directory (config.yaml + schema; each yak is one file, `.yaks/<herd>/yaks/<id>.md`, with a `status:` field). Works without an existing farm
  skills             Install the bundled agent skills (yaks, yaks-tracker) into a skills directory. Works anywhere — no farm required
  rollup             Group yaks by the external issue they roll up to
  doctor             Read-only farm-integrity check: report an invalid `status:` value, one id in two yak files, and dangling parent/depends_on references. Exits non-zero when any issue is found
  preflight          Read-only landing-readiness check for a team farm: nothing under `.yaks/` untracked or with unstaged changes in git, the verify command of each shorn yak in the change last PASSed, no invalid `status:` value, no id in two yak files. Prints one line per failure and exits non-zero, else `preflight: ok`. A private farm skips the git check (said so) and checks every shorn yak. With `--push-main` also checks that the `local` remote is the human's checkout (not bare, has `main`, not dirty on `main`) before `git push local <branch>:main`; read-only, never pushes. On a farm that is a branch, uncommitted yak files are one warning (`run yaks commit`), not a failure
  sync               Sync the farm branch with its remote: commit what is dirty (`yaks commit`), fetch and rebase onto `<remote>/<branch>` (concurrent edits to one yak merge into a valid yak through yaks's merge driver, which this registers), then push, creating the remote branch with the same name on the first publish. The remote is `branch.<branch>.remote`, else `origin`. Only for a farm on its own branch; runs in the farm worktree whatever the cwd. A private farm (`yaks private`) is never pushed. A rebase that stops on a conflict the driver cannot settle (a non-yak file such as `config.yaml`) is aborted, leaving the branch as it was, and names the files. Nothing is ever synced automatically
  commit             Commit the farm's own changes (everything under `.yaks/`: yak files, attachments, config) and nothing else, with a generated message such as `yaks: shorn yaks-abc1; updated yaks-def2`. Code staged or modified elsewhere is left alone (staged files stay staged). Runs a normal `git commit`, so the repo's hooks apply; never pushes. Fails in a private farm (nothing under `.yaks/` tracked by git) and while a merge or cherry-pick is in progress (git forbids a partial commit then; finish it with a plain `git commit`); a farm with no changes is a no-op that exits 0
  land               Land a Delta worker's commit by SHA on the current branch of the code checkout you are in: one single-parent squash commit with the worker's message and author plus a `Squashed-from: <full sha>` trailer (never a merge commit), or a `git cherry-pick` when the worker's base is no longer an ancestor of HEAD or the merge would conflict. Delta's applied state (a pending merge, the worker's files in the working tree) is not trusted: it is reported, then cleared, and the result is checked against `git merge-tree --write-tree`. Refuses (exit 3) when the working tree holds changes the worker's commit does not explain, unless `--force-discard`; refuses (exit 6) a SHA that is already an ancestor of HEAD but whose change is missing from HEAD's tree (a merge that dropped it); refuses (exit 7) a commit that touches `.yaks/` when HEAD tracks none (a branch farm). Never pushes. Needs git 2.38+ (2.40+ to check an already-landed SHA) and no farm
  status             Show what the farm has changed that git does not have yet, one line per yak in yak terms (`created`, `moved hairy -> shaving`, `notes +2`, `edited`, `removed`, `artifacts`; `config` for config.yaml), `*` marking what is staged, ordered by id, then what `yaks commit` would do (and its message). Uses the same classification as `yaks commit`. Read-only. Code changed elsewhere in the repo is only counted, never listed. A clean farm prints `farm clean: nothing to commit`; a private farm (nothing under `.yaks/` tracked by git) says so; both exit 0. While a merge or cherry-pick is in progress it says `yaks commit` will refuse. When the farm is a branch, a last line says whether that branch is published, ahead or behind its upstream, as of the last fetch (never fetches)
  brief              Print the worker brief for one yak: what a cold worker needs to start, derived from the yak, the config and the farm mode. Names the yak and that it is already `shaving`, the `YAKS_ACTOR=<name>` prefix for every command (plus `YAKS_DIR` for a private or pointer farm, or with `--yaks-dir`), this binary's path, the yak's `verify:` gate (else the config default), the forbidden moves, how to finish (team: one commit with the yak move; private: no yak ids in commits), how to ask, the `Decision:` note rule and the final-message format. Read-only. Claim the yak first (`yaks shave`): an unclaimed yak still prints, with a warning on stderr. An unknown id fails with nothing on stdout. The coordinator adds what a yak cannot know (spawn title, landing, model)
  tui                Open the interactive terminal UI
  help               Print this message or the help of the given subcommand(s)

Options:
  -C <PATH>          Run as if started in <PATH> (like `git -C`): farm discovery, `sheds`, `discover`, `commit`, `init`, `skills` and every other command see <PATH> as the current directory. A relative <PATH> is resolved against the real cwd; repeated `-C` compose, each relative to the previous. `$YAKS_DIR` still wins over discovery (a relative one is read from <PATH>)
      --shed <SHED>  Run as if started in another checkout of this repository (a shed from `yaks sheds`), picked by name like `yaks changes <SHED>`: its path, Delta dir id, thread-title slug, branch, actor, or a unique substring (`main` is the primary checkout; naming the checkout you are in is a no-op). The same as `-C <that shed's path>`: FULL access, so a write command writes in that shed's farm. Applied after any `-C`, relative to that checkout; at most once. No or an ambiguous match lists the sheds and exits 1. Never records the Delta thread title (that belongs to the checkout you are in)
  -h, --help         Print help
  -V, --version      Print version
