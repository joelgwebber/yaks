Implements `yaks-a3fc` on the pieces that now exist: checkpoint notes (`--meta kind=checkpoint --meta branch=<b> --meta commit=<sha>`, `71ca61e`), landed notes from `yaks land` (`7e4a014`), `yaks commits` reading recorded shas, and sheds built from notes (`7393e45`).

## Scope

1. **`yaks commits <id> --fetch`.** For each distinct `branch` in the yak's notes that has a `remote` (default `origin`), run `git fetch <remote> <branch>` in the code repo, then list `git log --oneline <base>..<remote>/<branch>`. `base` is the note's `base` key, else the code repo's default branch (`origin/HEAD`, else `main`). Mark the recorded checkpoint commit in the list, and say when it isn't on the fetched branch (rewritten or not pushed). Without `--fetch`, use the remote-tracking ref already there, and say it may be stale. Also in `--json`.
2. **Sheds rows show where an actor's code is.** If the actor's latest `checkpoint` note (on any yak) names a branch, show `branch <b> @ <short sha> (<ago>)` on its row, in text, JSON and the TUI Sheds tab detail. No fetching here.
3. **Docs and help:** `docs/cli.md` (`commits`, `sheds`), `docs/tui.md` if the tab changes, `--help`. Not `.agents/skills/`.

Decision: base for `git log base..branch` is the newest `base:` meta on the notes recording that branch, else `refs/remotes/<remote>/HEAD` (or `origin/HEAD`), else a local `main`. A `base:` is tried as given, then under the remote. Rejected: always `origin/main` (wrong for other default branches); a `--base` flag (the note already says where a worker forked, and the farm is shared).

Decision: branches are grouped by `(remote, branch)` over every note with a `branch:` key EXCEPT `kind: landed` notes, whose branch is HEAD at landing, not the worker's. Rejected: only `kind: checkpoint` notes (a hand-written note with `branch=` is just as good a record, and the design says only that the yak "records the connection").

Decision: `--fetch` runs `git fetch --quiet <remote> +refs/heads/<branch>:refs/remotes/<remote>/<branch>` with `GIT_TERMINAL_PROMPT=0`. The explicit refspec updates the tracking ref even in a clone that has a narrow `remote.<r>.fetch` refspec, which plain `git fetch origin <b>` does not reliably do. Rejected: `git fetch origin <b>` alone (updates only FETCH_HEAD in older/narrow setups).

Decision: a failed fetch prints `fetch failed: <git's message>` on that branch and still falls back to whatever remote-tracking ref exists; if there is none it also says `no remote-tracking ref ...`. Exit stays 0. Rejected: skipping the branch on fetch failure (an old ref is still useful, and the line says it failed).

Decision: each recorded checkpoint sha is classified `on_branch` (in base..branch, marked `← checkpoint`), `in_base` (an ancestor of the branch but not in the log: landed/merged) or `not_on_branch` (reported as NOT on the branch: rewritten or never pushed). Rejected: a boolean (an already-landed checkpoint is not a problem, and would read as one).

Decision: a sheds row's checkpoint is the actor's latest note with `kind=checkpoint` and a non-empty `branch` across all yaks; a checkpoint with a branch but no commit prints `branch <b> (<ago>)` without `@`. The TUI shows it as a dim first line of the detail pane, not on the list row (list rows are width-tight). Rejected: any note with a `branch:` (landed notes would show `main`); a list-row column.

Decision: no `.agents/skills/` edit (yakherd's). Skills should say: record a checkpoint with `--meta kind=checkpoint --meta branch=<b> --meta commit=<sha>` (optional `remote=`, `base=`), push first and then record; `yaks commits <id> --fetch` shows the branch's commits and marks the checkpoint, and says when the recorded sha is not on the branch; `yaks sheds` rows show `branch <b> @ <sha> (<ago>)` from the actor's latest checkpoint on any yak, never fetched.

## End-to-end check, two clones of one bare origin

A runner clone shaves, commits twice, pushes `work/w-1`, records a checkpoint and syncs. On the human's clone after `yaks sync`:

```text
w-1  active · just now
  branch work/w-1 @ 3d56301 (just now)
  shaving  t-9bb0  Remote work

Branch origin/work/w-1 (since main):
  fetched just now
  3d56301 t-9bb0: part two  ← checkpoint
  e049a1a t-9bb0: part one
```

Then `yaks land` on the human's side recorded `landed 3d56301 on main`, and `commits` lists both the checkpoint and the landing.

## Found: a `yaks/...` work branch can't exist beside the farm branch

The first run used `yaks/w-1/work`, the naming the `yaks-a3fc` decision suggested. `git checkout -b` failed: `cannot lock ref 'refs/heads/yaks/w-1/work': 'refs/heads/yaks' exists`. So nothing was pushed, and the checkpoint named an unfetchable branch. Fixed in `028a8e3`: `update` warns on a `branch=` value under the farm branch's name; docs, test examples and skills say never use that prefix (`work/...` in examples).
