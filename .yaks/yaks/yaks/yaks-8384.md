Generalize frontmatter so yaks, pages, sources and schemas share one field model, and so adding a field to yaks (`commit:`, `due:`, `recur:`) is a declaration rather than edits to `Task`, `parse_task`, `write::frontmatter`, the merge driver, JSON output and the TUI.

## Today

- `model::Task` has a fixed field set; `store::parse_task` is a hand-rolled line parser; anything else is kept as raw lines in `Task::extra` and re-emitted after the known fields.
- Nested values (a list of maps, `{by, at}`) only survive as opaque `extra` lines; nothing can read or edit them.
- `mergedriver` merges each known field by hand; unknown fields aren't merged at all.
- Note metadata (`yaks-6a11`) is already open-ended `key: value` with reserved keys: the model to follow.

## Proposal

- **One document model:** `Doc { fields: Fields, body }`, where `Fields` is an ordered map from key to `Value` (string, number, bool, list, map). Values are parsed from a YAML subset: block and flow scalars, lists and maps, comments kept. No anchors, tags or multi-document input. Unknown keys and their formatting round-trip byte for byte. Editing one key rewrites only that key's lines.
- **A field spec** per key: kind (`text`, `int`, `date`, `datetime`, `id`, `ids`, `list`, `map`, `url`), a merge rule (`three-way`, `max`, `union`, `ours-and-note`), and an optional default. The yak schema is built in (id, title, status, type, priority, created, updated, parent, depends_on, labels, source, prs, needs, verify) and a farm can **extend** it in `schemas/yak.md` (`due: {type: date}`, `commit: {type: list}`), never redefine built-in keys. Pages, sources and schemas get theirs from `schemas/<type>.md`.
- `Task` keeps typed accessors for the built-in fields, so the 4k lines of callers don't churn. New fields are read through `task.fields.get("due")`.
- **Performance:** the hand-rolled fast path stays for loading lists (id, status, title, priority, labels, parent, deps); full parsing happens on demand. `yaks-e61e` (startup cost at 10k yaks) must not regress.
- **Dependency:** I'd keep the parser hand-written (a few hundred lines, exact round-trip, which off-the-shelf YAML crates don't give us), not take `serde_yaml` (deprecated) or `saphyr`.

## Vocabulary collisions

- `type`: in a yak it stays the yak's kind (task, bug, idea). A document's kind comes from where it lives (`<herd>/yaks/` is a yak), so there's no clash in practice. Pages use OKF's `type`.
- `labels` (yaks) vs `tags` (OKF pages): keep each name in its own kind. Queries and the TUI treat them as one facet (`--label` matches page tags).
- `updated:` stays on yaks (the Recent view and sheds read it); the merge driver resolves it as `max`, so it never conflicts. Pages don't get one; git has the date.

Decision (Joel, 2026-11-01):

1. Hand-written YAML-subset parser, kept simple and easy to change (built in yaks-1f34).
2. Farms extend yak fields in `schemas/yak.md`; built-in fields can't be redefined. The same mechanism carries known tags with descriptions, the "label schema" asked for in yaks-640a and yaks-f04d.
3. **Changed from the lean: normalize now, everything is `tags`.** Yaks' `labels:` becomes `tags:` in the schema-7 migration, alongside the new reserved names. CLI flags follow (`--tags`, `--tag`, `--add-tag`, `--remove-tag`); the old `--label*` spellings stay as hidden aliases so existing scripts and skills keep working through the transition.
