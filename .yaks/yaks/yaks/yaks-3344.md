Found 2026-10-10 (Joel's run). From the primary checkout, `yaks changes main` (and `--shed main`, `answer <id>@main`) silently returned the changes of the one Delta clone, because `sheds::resolve` runs over the OTHER sheds only: the primary is not in the list when the viewer is the primary, so rule 4 (`main` = the primary) finds nothing and rule 5 (a branch named `main`) matches every Delta clone, which is usually on `main`.
Fix: `main` never falls through to the branch rule. When no primary is among the candidates, it is an error that says so (`main` is the primary checkout; it is this checkout, or not visible from here). A branch literally named `main` on a non-primary shed stays reachable by its dir id, slug or path.
Evidence (test fails first): a shed list with a non-primary shed on branch `main` and no primary: `resolve("main")` is an error, not that shed. With a primary in the list it still resolves to the primary. Real machine: `yaks changes main` from ~/src/yaks with one clone no longer prints the clone's changes.
Out of scope: showing the current shed as a row (the yak below), which will change what the list holds.
